# ADR-001: Использование PostgreSQL JSONB вместо MongoDB

- **Статус:** Accepted (2026-07-23)
- **Контекст:**  
  Sentinel должен хранить как структурированные данные книг (title, price, url), так и полуструктурированный `raw_data` (исходный HTML страницы, метаданные парсинга). На старте рассматривались два варианта: PostgreSQL для структурированных записей + отдельная MongoDB для сырых данных, либо только PostgreSQL с использованием колонки JSONB.
- **Решение:**  
  Использовать единую PostgreSQL и хранить `raw_data` в колонке JSONB.
- **Обоснование:**
  - Снижение операционной сложности: не нужно разворачивать, мониторить и бэкапить вторую СУБД.
  - JSONB поддерживает индексацию (GIN), что позволяет делать выборки по содержимому сырых данных без отдельного поискового движка.
  - В рамках Q1 объём данных невелик (сотни–тысячи записей), и PostgreSQL справляется с нагрузкой без необходимости в горизонтальном масштабировании.
  - Учебный план v2 явно исключает MongoDB из основного курса как избыточную для текущих целей.
- **Альтернативы:**
  - *MongoDB* — отличный выбор для гетерогенных документов, но добавляет лишнюю зависимость, требует отдельных навыков администрирования и усложняет docker-compose. Может быть рассмотрена в after-course, если потребует целевая вакансия.
- **Последствия:**
  - Упрощается `docker-compose.yml` (на 1 сервис меньше).
  - Миграции (`alembic`) покрывают и схему структурированных данных, и эволюцию JSONB (через сырые SQL-запросы при необходимости).
  - Запросы к JSONB менее удобны, чем нативный MongoDB Query Language, но для текущих задач (поиск по полю `html`, проверка наличия ключа) этого достаточно.
